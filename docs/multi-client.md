# Экземпляр под клиента

Схема, при которой вы обслуживаете нескольких клиентов, **не проходя App Review** у Meta.

## Почему это работает

App Review нужен только для того, чтобы **посторонний** человек подключил свой Instagram к **вашему** приложению Meta. Если у каждого клиента своё приложение, а его аккаунт добавлен туда тестировщиком, — постороннего нет. Клиент подключает свой аккаунт к своему приложению.

Публикация приложения (Live) при этом нужна: без неё Meta не доставляет вебхуки, а без вебхуков не работает ничего — чтение комментариев через API в режиме разработки урезано. Но публикация App Review не требует, достаточно заполнить URL политики, соглашения и удаления данных. Это проверено на боевой установке.

Итого на клиента: своё приложение Meta, свой поддомен, свой экземпляр, свои ключи. Верификация бизнеса и скринкасты не нужны никому.

## Архитектура

Общие Postgres и Redis, отдельные web и worker на каждого клиента:

```
                    nginx (по vhost на клиента)
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
   client-a          client-b          client-c
   web + worker      web + worker      web + worker
        │                 │                 │
        └─────────────────┼─────────────────┘
                          │
              postgres (по БД на клиента)
              redis    (по номеру БД на клиента)
```

Разделение по данным полное: у каждого клиента своя база в Postgres и свой номер логической базы в Redis. Ни строки кода менять не нужно — всё задаётся в `.env`:

```
DATABASE_URL=postgresql://openreply:PASS@postgres:5432/client_a
REDIS_URL=redis://redis:6379/3
```

BullMQ уважает номер базы в URL, Prisma — имя базы. Очереди клиентов не пересекаются.

**`ENCRYPTION_KEY` у каждого клиента свой.** Это не формальность: ключ шифрует токены Instagram, и общий ключ означал бы, что компрометация одного клиента вскрывает всех.

## Сколько влезает

Замеры с боевой установки:

| Компонент | Память |
| --- | --- |
| web | 291 МиБ |
| worker | 239 МиБ |
| postgres | 43 МиБ |
| redis | 8 МиБ |
| образ Docker | 2.51 ГБ, один на всех |
| база одного клиента | ~10 МБ |

Общие Postgres и Redis стоят 51 МиБ на всю установку. Каждый следующий клиент добавляет только web и worker — **около 530 МиБ**.

| Сервер | Клиентов |
| --- | --- |
| 8 ГБ | 12–13 |
| 16 ГБ | 26–28 |
| 32 ГБ | 55+ |

Процессор простаивает: при обычной нагрузке 0.0–0.6%. Упрётесь в память, не в CPU.

Диск: образ 2.51 ГБ один раз, базы по 10–100 МБ, логи ограничены. 60 ГБ хватает надолго.

## Что нужно завести на клиента

Долгая часть — Meta, и она делается руками. Остальное автоматизируется.

**1. Приложение Meta** (~1 час в первый раз, дальше 20 минут)

- Тип Business, сценарий «Manage messaging and content on Instagram». Не Facebook Login, не Marketing API
- Забрать `INSTAGRAM_APP_ID`, `INSTAGRAM_APP_SECRET` (страница Instagram) и `FACEBOOK_APP_SECRET` (App settings → Basic)
- Добавить аккаунт клиента Instagram-тестировщиком **и принять приглашение в самом Instagram** — половину пропускают, получают «Insufficient Developer Role»
- OAuth redirect URI: `https://КЛИЕНТ.вашдомен/api/instagram/callback`
- Вебхук: `https://КЛИЕНТ.вашдомен/api/webhook`, подписка на поле `comments`
- Опубликовать приложение (Live), заполнив три URL политик — их отдаёт сам экземпляр

Чьё это приложение — вопрос договорённости. Под аккаунтом клиента честнее: он владеет доступом к своему Instagram и может отозвать его сам. Под вашим — быстрее, но вы держите его данные.

**2. Аккаунт Instagram** должен быть Business или Creator. Личный подключить нельзя.

**3. Поддомен** `клиент.вашдомен` → A-запись на сервер.

**4. Экземпляр** — провижининг-скрипт: база, `.env` со свежими секретами, vhost, сертификат, запуск.

**5. Resend** — общий на все экземпляры. Один ключ, отправитель на вашем домене. Клиенты получают письма входа с вашего адреса, это нормально и даже правильно с точки зрения бренда.

## Автоматизация

Скрипт `provision.sh КЛИЕНТ` должен делать:

1. `CREATE DATABASE client_x` в общем Postgres
2. Выбрать свободный номер базы Redis
3. Сгенерировать `.env`: `NEXTAUTH_SECRET`, `CRON_SECRET`, `ENCRYPTION_KEY`, `WEBHOOK_VERIFY_TOKEN`, подставить общий ключ Resend
4. Поднять compose-проект с уникальным именем (`-p openreply-client-x`) и портом на `127.0.0.1`
5. Сгенерировать vhost nginx, выпустить сертификат
6. Накатить миграции
7. Напечатать `WEBHOOK_VERIFY_TOKEN` и оба URL — их вставлять в консоль Meta

Секреты Meta вписываются после создания приложения, отдельной командой.

Основа уже есть: `deploy/gen-env.sh`, `deploy/bootstrap.sh`, `deploy/nginx-openreply.conf`. Нужна надстройка, которая разводит клиентов по базам, портам и именам проектов.

## Эксплуатация

**Обновление версии** — пересобрать образ один раз, перезапустить экземпляры по очереди. Образ общий, так что сборка одна на всех.

**Бэкапы** — `pg_dumpall` вместо `pg_dump`, плюс архив всех `.env`. Без `ENCRYPTION_KEY` дамп клиента бесполезен.

**Токены** продлеваются кроном автоматически. Крон-задачи нужны свои на каждый экземпляр, либо один скрипт, обходящий все.

**Мониторинг** — у каждого экземпляра есть `/api/health` с состоянием базы, Redis, очереди и живостью воркера. Обходить их по кругу и слать уведомление при `worker.healthy: false` — минимально достаточно.

**Лимиты Meta** — 750 сообщений в час на аккаунт. Ограничитель уже встроен и работает на аккаунт, а не на установку, так что клиенты друг другу не мешают.

## Риски

**Доступ из России.** Ваши клиенты упрутся в то же, с чем вы боролись: зарубежный IP режется провайдерами, Cloudflare рвёт HTTP/2. Для одного человека решается relay через российский сервер, для десятка — это уже отдельная инфраструктура. Заложите это в план, а не оставляйте на «разберёмся потом».

**Meta меняет API.** Приложения ломаются от изменений на стороне Meta, и чинить придётся все экземпляры сразу. Один клиент — своя боль, двадцать — работа.

**Один сервер — общий отказ.** Общие Postgres и Redis означают, что их падение роняет всех. Для двух-трёх клиентов терпимо, для двадцати нужна реплика.

**Приложения Meta могут блокировать.** Автоматизация переписки — зона повышенного внимания Meta. Если заблокируют одно приложение, остальные не пострадают: это и есть главное преимущество схемы перед общим сервисом, где блокировка убивает бизнес целиком.

## Когда эта схема перестаёт подходить

Примерно на двадцати клиентах ручная возня с приложениями Meta начинает съедать больше времени, чем приносит денег. К этому моменту имеет смысл считать экономику App Review: разовые вложения в верификацию бизнеса против постоянных затрат на онбординг. Но до двадцати клиентов схема «экземпляр под клиента» дешевле и безопаснее.
